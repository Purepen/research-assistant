Foundations

The mobile navigation model

02 / 14
Today

The desktop layout simply collapses: the 232px sidebar disappears below 860px and all navigation moves behind a hamburger + slide-out drawer. Every destination costs two taps, current location is invisible, tap targets are desktop-sized (~32px), tables and multi-column grids overflow, and page headers scroll away.

Proposed

A persistent bottom tab bar — the four destinations that matter, always one thumb-tap away, with the app's single most important action (New Spec) as a raised center button:

  • 1Home — dashboard overview & recent activity
  • 2Projects — every generated specification
  • 3New Spec — center FAB, opens the Generate wizard
  • 4Topics — the Topic Lab toolset
  • 5Profile — account, API key, model tiers
Why a tab bar, not the drawer This app has exactly 5 destinations — the textbook case for bottom tabs (Apple HIG & Material both). Navigation is always visible, state is self-evident, and reach is thumb-native. The drawer pattern exists for apps with 7+ sections; here it only hides the product.

Global rules
  • • Touch targets ≥ 44×44px, list rows ≥ 56px
  • • Inputs ≥ 16px font — prevents iOS auto-zoom
  • • One column everywhere; tables become cards
  • • Sticky app bar: page title + avatar, 56px
  • • Sticky bottom CTA on forms (never below the fold)
  • • Type: Sora headings · DM Sans UI · Fraunces/serif for document reading
  • • Existing tokens unchanged: #16a34a on white, #0f1f0f ink

Implementation

How to ship this incrementally

14 / 14
Order of work
1 · Tab bar + app bar shell ~1 day

One new component pair in dashboard/layout.tsx behind the existing 860px breakpoint. The drawer and hamburger are deleted, not maintained in parallel. Desktop keeps the sidebar untouched.

2 · Dashboard, Projects, Profile ~2–3 days

Mostly CSS restructuring: single column, cards instead of tables, stat tiles. The data hooks (useProjects, useUser) are reused as-is. Consolidate the three duplicated status-color functions into one helper while touching all three pages.

3 · Generate wizard + spec reader ~3–4 days

Real component work: step state for the wizard, accordion + pills for the reader, progress ring for the live state. The polling infrastructure already exists; only presentation changes.

4 · Topic Lab split ~1 week

The big one: break the 1,160-line page into per-tool routes, moving its raw-axios calls onto lib/api.ts + React Query in the same pass (fixing the known 401-handling gap). Do it last; everything else ships without it.

Ground rules
  • • No new design language. Every screen uses the existing tokens (#16a34a green, #0f1f0f ink, existing badge/card/button classes). This proposal adds layout patterns, not a theme.
  • • No new dependencies except optionally vaul (bottom sheets). Icons come from lucide-react, already installed — retiring the ~90 hand-rolled SVGs as pages are touched.
  • • Accessibility is built in, not bolted on: every tap target is a real <button>/<a>, 44px minimum, with focus-visible states — fixing the current div-onClick pattern as each screen is rebuilt.
  • • Browser-native alert()/confirm() are replaced by bottom sheets as each destructive action is touched.
What this buys beyond mobile The wizard steps, action sheets, status helper and typed section components are all reusable on desktop — this is the first concrete step toward collapsing the four coexisting design systems into one.
Companion document The full-frontend aesthetic redesign (desktop) is proposed separately in frontend-redesign-proposal.pdf — same tokens, same components, one unified system across both form factors.
